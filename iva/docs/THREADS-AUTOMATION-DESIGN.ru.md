# Постоянное продвижение Автоотклик AI через Threads

Проект решения от 23 октября 2026 по поручению владельца. Это схема реализации; Threads worker и публикации пока не включены. Наблюдения по настоящей ленте и исходные договорённости: THREADS-AUTOOTKLIK.ru.md.

## Уточнение владельца: выбран браузер

В последующем сообщении владелец выбрал браузерную автоматизацию с сохранённой авторизацией вместо API. Это актуальное решение; рекомендации API ниже остаются историей рассмотренного варианта. Текущая сессия встроенного браузера Codex suer_stuff проверена, но доступный инструмент не предоставляет её подключения к автономному процессу на VPS. Поэтому для серверного исполнения готовится отдельный сохраняемый профиль того же аккаунта с ручным входом владельца. Перенос cookies/паролей из Codex не выполнялся.

Подготовка серверного входа: deploy/threads_browser_login.py; профиль /opt/iva/data/threads-browser/profile, статус /opt/iva/data/threads-browser/status.json, браузерный lock. threads-display/browser/wm/vnc/webview используют отдельный threads.slice; просмотр только через SSH-туннель deploy/threads_ui_tunnel.py на http://127.0.0.1:15082/vnc.html?autoconnect=1&resize=remote. Эти сервисы подготовки входа не включены в автозагрузку и не публикуют комментарии. Полный исполнитель очереди и инструмент Ивы ещё не установлены. Работоспособность входа нельзя считать подтверждённой до состояния authenticated и проверки аккаунта suer_stuff. Профиль и службы MAX не меняются.

Экран входа на VPS фактически открыт и проверен через noVNC. Прямое соединение Threads с VPS истекало по таймауту; только threads-browser получает THREADS_BROWSER_PROXY=http://10.203.77.2:8888. Полная публичная страница через этот прокси возвращает HTTP 200. Для устойчивой работы с прокси в этом браузере отключены QUIC/HTTP2, GPU acceleration; общий браузер Ивы и маршруты других приложений не менялись. Серверные порты 16082 (webview) и 5982 (VNC) слушают loopback, первоначальная отладочная CDP-настройка удалена. Лимиты threads.slice: CPU 60%, MemoryHigh 640M, MemoryMax 768M, swap 128M; запуск откладывается при MemAvailable ниже 640 МБ. Это измеряемый дополнительный расход памяти, а не свидетельство готовности постоянного worker. Службы подготовки входа останавливать через systemctl stop threads-browser threads-webview threads-vnc threads-wm threads-display, сохраняя профиль.

В действующей авторизованной сессии Codex дополнительно проверен браузерный поиск «отклики hh». Top отдавал старые обсуждения; для свежего отбора наблюдался реальный URL https://www.threads.com/search?q=отклики%20hh&filter=recent после выбора Recent. При реализации проверять дату поста даже в этом режиме. Никаких комментариев в ходе проверки не отправлено.

## Цель и границы

На активном VPS Ивы 5.63.152.247 находить обсуждения, в которых автоматизация откликов на hh.ru соответствует запросу человека; изучать пост и доступные ответы; готовить и публиковать комментарий от suer_stuff; учитывать реакции и сообщать владельцу по необходимости. Ива принимает команды на управление, но не держит постоянный диалог модели в ожидании событий.

Факты о продукте брать из версионируемой карточки: ссылка Chrome Web Store, работа на hh.ru в браузере, сравнение резюме с вакансиями, письма и отправка через расширение, действующие цены/пробные условия и готовые функции. SMTP/OAuth и другие незавершённые возможности не рекламировать как проверенные. Не придумывать отзывы, личный пользовательский опыт, бесплатность, гарантии трудоустройства или повышение зарплаты. Рекомендация от создателя должна быть узнаваема как рекомендация собственного продукта.

## Компоненты

1. `iva@threads`: отдельный systemd worker с heartbeat, сохранённым расписанием, ограничением времени/памяти и восстановлением после перезапуска.
2. `threads_promotion` native tool Ивы → отдельный маршрут gateway. Команды проверяются по текущему прямому поручению владельца. Текст Threads, ответы пользователей и результаты модели не могут менять режим, лимиты, учётную запись или правила.
3. Собственная SQLite `/opt/iva/data/threads-promotion.sqlite3` для очереди, курсоров, конфигурации, планов публикаций, истории и уведомлений. Финансовая SQLite Ивы не используется для хранения состояния продвижения.
4. Адаптер Threads с раздельными возможностями discovery/read/publish/reconcile. Предпочтителен официальный API для доступных операций. Возможности проверяются реальными вызовами с выданными разрешениями, а не предполагаются по наличию страницы в браузере.
5. Модель получает только карточку продукта и ограниченный текст выбранного обсуждения. Возвращает структурированные fit/reason/target/draft, не исполняет инструменты и не владеет аккаунтным токеном.
6. Исполнитель публикации отдельно проверяет разрешённый режим, конфигурацию, лимиты, совпадение аккаунта и актуальность контекста. Доступ к сети/токену имеет транспорт, а не текст модели.
7. Отдельная очередь уведомлений в Telegram владельца с учётом неопределённой доставки. При реализации нужен тест, что фоновые события не создают второй poller Telegram.

Существующий scheduled_worker Ивы намеренно ограничен чтением: его нельзя просто снабдить произвольным shell или правом отправки сообщений. Для Threads вводится самостоятельная ограниченная операция публикации с собственным постоянным разрешением и журналом. Существующие почтовые, календарные и финансовые задания сохраняют прежние границы.

## Источники обсуждений

Два источника, объединяемые по идентичности поста:

- Публичный поиск: темы hh.ru, ручные отклики, сопроводительные, долгий поиск, поиск удалённой работы. Список запросов меняется по команде владельца; объединяются свежие и релевантные результаты.
- Персональные рекомендации suer_stuff, если в выбранном серверном адаптере получится подтверждённый доступ к ним.

Официальная коллекция Meta документирует OAuth, публикацию и reply_to_id. Полный набор разрешений для поиска публичных постов, чтения чужих обсуждений и ответов им надо подтвердить на реальном аккаунте. Официальную страницу keyword search в ходе исследования не удалось прочитать из-за ограничений сайта; точные доступы и квоты не следует обещать на основе сторонних пересказов.

Доступ к персональной For you через API не подтверждён. Приоритет поиска по ключевым темам — инженерная рекомендация для стабильного охвата, а не утверждение, что API отдаёт персональную ленту. Если нужен серверный браузер, владелец входит в отдельный профиль Threads непосредственно на VPS. Текущая авторизация во встроенном браузере Codex сама на VPS не переносится. Профиль MAX не переиспользуется, его защита не обходится. CAPTCHA/запрос нового входа переводят работу в needs_login и требуют действия владельца; автоматического обхода нет.

Сетевой доступ и ресурсная нагрузка Threads на VPS ещё не проверены. Если доступ требует изменения маршрута, выбирать его явно и отдельно; не менять общий маршрут Ивы/Cartesia/SSH и не считать её Codex VPN готовой универсальной настройкой Threads.

## Один цикл

1. Проверить enabled/mode, рабочее время, бюджет вызовов/публикаций и здоровье транспорта.
2. Собрать ограниченную порцию постов, сохранить источник/время и устранить повторы по post ID, нормализованному permalink и корневой ветке.
3. Дешёвый отсев без модели: язык, давность, исключённые авторы, уже обработанные темы, отсутствие продукта/площадки, собственные публикации.
4. Для кандидата прочитать пост, доступные значимые ответы и выбранную подветку. Зафиксировать границы чтения: скрытые/недоступные ответы не считать прочитанными.
5. Классифицировать: ручная рутина hh; активный поиск с неясным этапом; проблема вне возможностей продукта; коммерческая/HR ветка; эмоциональная поддержка без запроса инструмента. Последняя сама по себе не повод продавать.
6. Выбрать `skip`, `clarify`, `recommend` или `handoff`. При неясной площадке/причине длительного поиска сначала уточнение. Не использовать просто ключевое слово «работа» как основание для комментария.
7. Сгенерировать короткий ответ на конкретную реплику. Для рекомендации использовать реальное авторство продукта. Ссылка добавляется по контексту; не вынуждать людей писать кодовое слово ради ссылки и не обещать ссылку в профиле до её фактического размещения.
8. Проверить факты, длину, повторы, отсутствие выдуманных результатов/навязчивых утверждений. Высокая оценка модели не заменяет эти проверки.
9. Сохранить неизменяемый план публикации: аккаунт, target/reply_to, текст, product_version, config_revision, основание и expiration.
10. Непосредственно перед отправкой повторно проверить паузу/лимиты и доступность целевого поста. Если контекст изменился или план устарел — перечитать и пересоздать план.
11. Публиковать последовательно. Сохранить ID/ссылку ответа после подтверждённого успеха.
12. Позже проверять новые ответы только в собственных подветках, отделяя интерес, вопрос, отрицательную реакцию и обычную реакцию. Существенные вопросы/жалобы и просьбы прекратить рекомендации направлять владельцу; не повторять предложение после отказа.

## Повторы и неопределённый результат

Состояния: discovered → reading → skipped/clarification/drafted → ready → sending → sent/uncertain/failed. Блокировка очереди и lease не позволяют двум экземплярам одновременно публиковать один план. Рабочая конфигурация должна содержать разрешённый аккаунт и сохранённое основание постоянного разрешения владельца.

Таймаут после отправки не означает неуспех. Сначала искать подтверждение в собственных ответах и учитывать внешний ID; не посылать тот же комментарий автоматически ещё раз. Если согласовать результат нельзя, сохранять uncertain и уведомлять. Exactly-once через чужой API/браузер не обещается. Временные ошибки чтения повторяются с ограниченной задержкой; 429 учитывает Retry-After и лимит платформы. При проблеме авторизации, ограничениях публикации или невозможности проверить результат отправка приостанавливается.

Пауза сохраняется немедленно и блокирует новые отправки. Уже принятый платформой запрос может завершиться; статус явно показывает sending/uncertain. Редактирование настроек не изменяет задним числом готовые планы — их требуется переоценить по новой config_revision.

## Управление через Иву

Предлагаемые операции инструмента: status, configure, start, pause, resume, stop, candidates, drafts, publish, reject, history, report. Точные имена схемы определяются при реализации. Примеры естественных команд:

- «Начни искать обсуждения про ручные отклики на hh».
- «Пока только готовь варианты, не публикуй».
- «Публикуй подходящие рекомендации по установленным правилам».
- «Снизь лимит до двух новых комментариев в день».
- «Поставь Threads на паузу».
- «Покажи последние комментарии со ссылками и почему ты выбрала эти ветки».
- «Что ответили на нашу рекомендацию? Кто заинтересовался?».
- «Исключи этого автора».
- «Сколько найдено, пропущено, опубликовано и потрачено за неделю?».

Режимы: monitor (только сбор), draft (сбор и тексты), auto (публикация по правилам). Постоянное разрешение владельца на auto позволяет работать без запроса согласия на каждый обычный подходящий комментарий. Для сообщений за пределами этого сценария требуется текущее отдельное поручение. Во время разработки не считать выбор режима активным до сохранения конфигурации и подтверждения живого worker.

## Предлагаемые стартовые настройки, ещё не включены

- Цикл поиска каждые 30 минут; новые рекомендации публиковать с 09:00 до 21:00 Asia/Yekaterinburg.
- Начальный редакционный бюджет: до 3 новых рекламных ответов в день, один на корневую ветку. Это размер первого эксперимента, а не «безопасный лимит Threads».
- На новом аккаунте сначала посмотреть выборку черновиков и откалибровать критерии, затем включить auto по постоянным правилам. Режим калибровки — рекомендация внедрения, не требование подтверждать каждый последующий комментарий.
- Все модельные вызовы, включая чтение/классификацию и продолжение диалога, имеют общий измеряемый бюджет. На этапе пилота записывать реальную стоимость и ограничивать число новых разборов; денежный потолок назначить по результатам замера и поручению владельца.
- Не запускать модель на неизменившихся ветках. Хранить хеш контекста/последние reply IDs и перечитывать изменения.

## Отчёты

По запросу: состояние worker/авторизации/режима, последний и следующий цикл, найдено/прочитано/пропущено/готово/отправлено/uncertain, причины пропусков, ссылки и тексты отправок, интерес/вопросы, расходы и остаток бюджета. Установки и конверсию не выводить из лайков: нужна реальная атрибуция или подтверждённый первый запуск. Доступные метрики указать отдельно от недоступных.

Без отдельной команды на ежедневную сводку не присылать одинаковые отчёты каждого цикла. Уведомлять о требуемом входе, ограничениях платформы, неопределённой отправке, исчерпании бюджета и существенном интересе/вопросе. Возможность ежедневной/еженедельной сводки включается отдельно. Публикации в Telegram выполняются только существующим разрешённым каналом владельцу, а не автоответами другим участникам Threads.

## Ресурсы и эксплуатация

На проверке VPS: RAM всего 1961 МБ, MemAvailable около 896 МБ, MAX slice около 561 МБ, hh-extens около 116 МБ. API-вариант предпочтителен для такого состава служб. Browser-вариант требует отдельного замера и ограничителя общей нагрузки/числа браузерных задач; при недостатке ресурсов откладывать Threads, сохраняя работоспособность Ивы и защиты MAX. Не запускать второй постоянно работающий Chromium без этой проверки.

Секреты аккаунта отдельно от исходников/журналов; в модели токены/пароли не передавать. База/конфигурация и журнал входят в резервные копии. Сырые страницы сохранять ограниченно, без ненужного сбора профилей и личной переписки. Ротация аккаунта/режима/правил имеет audit trail. После перезапуска не наверстывать пропущенные публикации пачкой: перечитать свежий контекст и соблюдать текущие правила.

## Последовательность реализации и проверки

1. Проверить на аккаунте реальные возможности поиска, чтения чужих ответов и публикации через Threads API. При отсутствии нужного доступа проверить отдельный серверный браузер, вход и ресурсный бюджет.
2. Реализовать очередь, карточку продукта, сбор/оценку и dry-run без внешних публикаций.
3. Подключить инструмент Ивы, естественные команды, status/report и Telegram outbox. Изолированно проверить owner binding и запрет команд из страниц.
4. Проверить pause/send race, restart recovery, dedupe, неясный результат, удалённый пост, смену аккаунта, лимит/бюджет, 429/login failure и отказ источника.
5. Проверить одну согласованную тестовую публикацию с сохранением ID/ссылки и последующим readback; не считать нажатие кнопки подтверждением отправки.
6. Откалибровать несколько выбранных владельцем черновиков и включить постоянный режим в заданных рамках. Отдельно пройти реальный пользовательский путь установки приложения, входа, первого запуска и оплаты перед масштабированием.

Неустановленные сейчас возможности: серверная авторизация Threads/API, полный доступ к персональной For you, права API на произвольные чужие обсуждения, автоматический исполнитель публикаций, инструмент управления Ивы и измерение конверсии. Этот документ не объявляет их работающими.


Исправление отзывчивости noVNC 23 октября: MemoryHigh 512M вызывал высокое memory pressure (some avg10 около 38%, full около 13%) при живом Chromium. Повышены только лимиты threads.slice: CPU 60%, MemoryHigh 640M, MemoryMax 768M, swap 128M сохранён. На контрольном замере доступная системная память выросла примерно до 767 МБ, pressure снижался. noVNC переведён на resize=scale вместо remote (Xvfb запрещает динамический resize). Без перезапуска аккаунтного браузера появилась форма Instagram входа; ручной ввод остаётся владельцу. Это не подтверждение авторизации или автопубликаций.


Проверка CAPTCHA 23 октября: на серверном экране Instagram recaptcha была явная ошибка Could not connect to the reCAPTCHA service. На замере давление памяти в покое было нулевым; публичные api.js Google/reCAPTCHA через host/proxy отвечали HTTP 200 за 0.08–0.36 секунды. Однократная обычная перезагрузка страницы восстановила виджет: изображения и Verify стали видны. CAPTCHA не решалась, дальнейшее прохождение оставлено владельцу. Во время перезагрузки был кратковременный рост memory pressure, поэтому полная интерактивная отзывчивость под любой нагрузкой не гарантируется. Новые повышения лимитов в этой проверке не выполнялись.

Последующее состояние 23 октября: владелец повторно сообщил о нехватке памяти. При 1961 MiB RAM Threads занимал около 639 MiB, MAX около 435 MiB; swap занят 1217 MiB.
