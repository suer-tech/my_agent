# Чередование MAX и Threads

Лимит Threads увеличен по прямой просьбе владельца 23.10.2026: MemoryHigh=896M, MemoryMax=1024M, MemorySwapMax=256M. Применено постоянным systemctl set-property без перезапуска браузера (PID сохранён). На замере до изменения Threads занимал около 639 MiB, MemAvailable=767 MiB; memory.events high=894086 при отсутствии OOM-kill. MAX Chromium остановлен, в очереди только интерактивный вход Threads. Это исправляет ограничение cgroup, но не увеличивает физические 2 ГБ VPS.

Уточнение владельца 23.10.2026: таймер применяется только при конкурирующих реальных фоновых заданиях ОБОИХ сервисов. Просто открытые окна и ручной вход не являются фоновыми заданиями, по времени они не переключаются. При работе только одного сервиса он продолжает работу. `switch` по прямой команде владельца остаётся доступен независимо от таймера. Текущий `threads` — интерактивный браузер; фонового исполнителя Threads ещё нет, поэтому автоматической ротации с ним сейчас нет. При установке будущего исполнителя его нужно зарегистрировать в `background_work` управляющего сервиса. Восемь тестов координатора (включая два новых условия) и три теста восстановления MAX проходят. При обновлении управляющего сервиса текущий процесс входа Threads сохранён.

Установлено на VPS 5.63.152.247, 23 октября 2026. Управляющая служба `iva-browser-coordinator` включена в автозагрузку. По умолчанию один ход — 15 минут. При наличии второй задачи после этого срока выставляется запрос уступить браузер; текущая задача завершает безопасное действие, сохраняет результат и закрывает Chromium. Следующая запускается только после выхода предыдущего владельца и освобождения его cgroup. Длительная операция продлевает ход: принудительной остановки по таймеру нет.

Общая блокировка `flock` не позволяет двум владельцам открыть Chromium одновременно. Дополнительно сохраняется прежняя отдельная блокировка профиля MAX. Запуск из панели MAX также проходит общий guard: если ход занят, процесс только ставит запрос в очередь и выходит с кодом 75. Панель может показать завершённый процесс до фактического запуска по очереди; актуальное состояние смотрит инструмент Ивы. При недоступности управляющего сервиса новые запуски запрещены. Его перезапуск не останавливает работающий браузер через systemd-зависимость.

## Управление Ивой

Нативный `browser_control`: status, enqueue, switch, remove, pause, resume, configure. Задачи: max-manual, max-worker, max-ads, max-broadcast, threads. Изменения доступны по текущему прямому сообщению владельца с точной цитатой, извлечённой из рабочего входящего сообщения Telegram; команды со страниц права не дают. Нет произвольных путей, команд shell или имён служб. Unix socket `/run/iva-browser/control.sock` доступен root/iva, проверяется UID клиента.

Примеры: «Покажи очередь MAX и Threads», «Переключись на Threads после текущей ссылки», «Продолжи чередование», «Поставь браузеры на паузу», «Делай ходы по 20 минут». accepted означает, что запрос сохранён, а не что текущая операция уже завершилась. status показывает текущий сервис, реальные живые владельцы, очередь, ошибки и курсор.

MAX worker/ads/broadcast можно продолжить, только если запуск уже разрешён в его панели (`*_launch.json enabled=true`). Инструмент не создаёт кампании, не включает отправку и не меняет её параметры. Пока активны только ручной MAX и браузер Threads. Самостоятельный legacy distribute_pages_links.py не имеет управляемого systemd-задания и блокируется; встроенная категоризация сборщика работает в его текущем ходе.

## Сохранение позиции MAX

- Сборщик: контрольная точка между ссылками, после сохранения результатов и дневной квоты. В `daily_state_*.json` остаются источник, выбранный диапазон, идентификатор запуска, завершённые URL и счётчики. При продолжении используется прежний `DAILY_WINDOW_START`, не создаётся новый проход. Для режима без дневного расписания дополнительно сохраняется набор обработанных URL, привязанный к отпечатку запуска.
- Классификация: сохранённые результаты пропускаются; следующая ссылка берётся из `ClassificationRun.pending()`. При передаче хода не сбрасывается enabled и не повторяется recheck.
- Рассылка: передача хода между получателями либо во время ожидания. Между записью sending и получением результата отправки передачи хода нет. `sent` сохраняется в SQLite; `uncertain` не отправляется автоматически повторно. При аварии оставшееся sending штатный код переводит в uncertain. Рабочие сообщения для проверки не отправлялись.
- Ручной браузер: штатно закрывается контекст, сохраняется постоянный профиль и адреса вкладок MAX без query/fragment. При открытии восстанавливается адрес. Несохранённый ввод в формах и положение прокрутки не являются гарантированным checkpoint автоматизации.
- Файл собранных ссылок больше не очищается при каждом восстановлении: существующий сбор сохраняется.

Состояние очереди и дополнительные курсоры: `/var/lib/iva-browser/state.json`, `grant.json`, `checkpoints/`. Секреты и cookies туда не копируются. Исходные пять файлов MAX до патча: `/opt/max-deploy/before-browser-turns/`; исходники исправлений — `deploy/install_browser_coordinator.py`, `deploy/browser_turn.py`, `deploy/browser_coordinator.py`. Не применять первоначальный установщик MAX поверх новых guard и контрольных точек.

## Проверка и ограничения

Девять изолированных тестов прошли на VPS: восстановление выбранного диапазона и следующей ссылки, классификация, продолжение синтетической рассылки без повтора sent/uncertain, очередь, мягкая пауза, перезапуск управляющего сервиса и блокировка второго владельца. Реально проверено переключение MAX → Threads → MAX и отказ второго запуска с exit 75. Настоящая Ива прочитала status новым инструментом; диагностических сообщений в MAX/Threads и Telegram не отправляли.

Отчёты: `/opt/iva/data/browser-turns-verification.json` и `browser-turn-routing-verification.json`. Интерактивную тяжёлую кампанию на реальных чатах не проверяли. Память после возврата MAX: MemAvailable около 714 MiB, без параллельного браузера Threads. Нет гарантии, что любое содержимое страницы поместится в прежний лимит MAX.

Threads пока имеет только отдельный постоянный браузер с сохранением профиля и безопасного адреса вкладки. Работник поиска/публикаций не установлен. На проверке серверный профиль вернул needs_login; сообщение владельца об успешном входе не подтвердило вход именно в этот профиль. Запрещено заявлять, что продвижение уже работает, или переносить cookies из Codex/Chrome.

При необъяснённом выходе браузера, остаточных процессах либо нехватке RAM очередь не запускает второй браузер. Ива может прочитать ошибку и после исправления причины возобновить/поставить задачу в очередь. После аварийной перезагрузки сохранённая очередь не доказывает завершённую отправку: проверять нативное состояние MAX. Отдельные автоматические уведомления о сбоях нового управляющего сервиса пока не добавлены; status доступен по запросу.
